---
description: 自动执行和落地阶段任务工作流 (Phase Execution Workflow)
---

这是一个规范化项目推进与代码落地的工作流，用于承接 Harness 辩证后形成的技术方案（如 `test_plan_XX.md`）。
其核心目的是规范化代码落地过程，并强制当前模型保持独立思考，避免产生降智幻觉和迎合倾向。

作为执行落地的大模型，你需要严格遵循以下步骤：

### 核心训诫 (Core Directives)：
- **绝不盲目迎合**：即使是用户或之前模型规划的方案，如果在实际阅读代码后发现明显会导致 Bug、循环依赖或破坏现有架构完整性的点，必须立刻尖锐指出并暂停执行！
- **全局防御视角**：保持如同 Harness 工作流中的批判精神，写代码前必须在脑内沙盘推演一次，确信无缺陷再动笔。

### 执行步骤：

#### 步骤一：深度理解与实施方案反刍 (Implementation Planning)
**[执行动作]**
1. 读取指定的 `Phase XX` 阶段任务或计划文档（例如: `MD Files/test_plan_XX.md`）。
2. 调用 `view_file` 或相关工具，**仔细检查**当前项目中将被影响的核心代码文件。摸清真实代码现状，不能纯靠猜测。
3. 帮用户创建或更新当前对话的 `implementation_plan.md` 伪影制品（Artifact）。将具体的代码落地方案拆解清楚，并在方案中明确**指出你所预见的并发、边界情况或历史包袱等潜在雷区**。
4. **注意**：在此步骤，**绝对不要修改任何代码，不要执行命令**，只做前期规划。
**[结束动作]**
保存 implementation plan 后，必须明确等待用户输入。向用户发送如下黑体提示：
**✅ 阶段落地方案已解析完毕，并生成了实施计划（参见 implementation_plan.md）。我已经审视了方案并加入了避坑思考，请您审查。回复“同意”后，我将正式开始改写代码；如有异议，请直接修改或指出。**

#### 步骤二：高标准的代码实施 (Rigorous Coding)
**[执行动作]** 
*（触发条件：用户明确回复同意后）*
1. 创建 `task.md` 制品作为 TODO List。
2. 独立开始执行代码修改（`replace_file_content` / `multi_replace_file_content`，尽量不要随意用脚本来暴力改）。
3. 每修改完一个关键文件或组件，就在 `task.md` 中打勾 `[x]`。代码必须高内聚低耦合，符合项目的 zero-extra-infrastructure 原则。

#### 步骤三：文档收尾与会话完结 (Documentation & Hand-over)
**[执行动作]**
所有代码修改和验证打勾完成后：
1. 更新主进度追踪文档，例如修改 `progress_report.md` 中的状态。
2. 创建或更新 `walkthrough.md` 总结改动和自测路径。
**[结束动作]**
向用户发送如下黑体提示：
**🎉 Phase 任务已全部落地且文档已更新完毕。为了保持极速的上下文响应和节省 Token，建议您现在关闭此会话。在进行下一个子阶段时开启全新会话，并直接发送 `/execute_phase [下一个Phase名称或文档]` 即可流畅互联。**
