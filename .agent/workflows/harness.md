---
description: Harness 辩证 + 证据门禁工作流 (原 5阶，现升级为 7阶段)
---

这是一个交互式的分步工作流，基于原有 **5段式辩证法 (Dialectic Method)** 升级为 **“辩证 + 证据门禁”7阶段流程**。作为当前被激活的 LLM，请你根据上下文历史判断目前处于工作流的哪一个阶段，**且每次回复只能执行一个阶段的任务**。执行完当前阶段后，**必须立刻停止**输出，等待用户切模型或给出下一步口令。绝对不要一次性跑完所有阶段。

## 证据铁律

- 凡涉及现有代码、Schema、CLI 行为、工具注册、测试结果、性能数据、依赖状态、线上或本地文件内容的断言，必须绑定至少一种证据：代码路径 + 行号、可复现命令、测试用例名、现成日志或 Artifact。
- 未实际验证的内容，只能写成“假设 / 预期 / 待验证”，不得写成“已接受 / 已通过 / 已证明 / 已上线”。
- 在【第六阶段】事实核验通过前，ADR 状态只能是 `Proposed`、`Candidate` 或 `Needs Validation`，禁止写 `Accepted`。
- 若证据与前序辩证结论冲突，必须回流到【第三阶段】或【第五阶段】修订，严禁硬落盘。
- 验收项必须是可执行、可复现、可失败的；不允许用与事实无关的“展示型命令”充当验证。

**上下文状态机：**
请仔细阅读此节点之前的聊天历史。首次触发此命令时为【第零阶段】。
若【第六阶段】失败且用户回复 `继续修订`，则回到【第五阶段】。
若【第六阶段】通过且用户回复 `开始落地`，则进入【第七阶段】。

### 【第零阶段】：事实基线盘点 (Evidence Baseline)
- **适合模型**：当前激活模型（优先具备代码检索 / 工具使用能力的模型，如 Claude 3.5 Sonnet）
- **角色**：仓库事实审计员 / Source-of-Truth 勘测员
- **任务**：在进入任何方案设计前，先建立事实基线。
  - 读取与本议题直接相关的代码、文档、测试、CLI、配置文件。
  - 列出本次讨论涉及的 **Source of Truth**：真实 Schema、真实命令行为、真实注册点、真实测试入口、真实现状限制。
  - 将信息分成三类：**已证实事实**、**待验证假设**、**当前未知项**。
  - 如果是纯新功能或纯绿地设计，也必须明确写出“当前仓库内无对应实现 / 无可核验事实基线”，而不是默认脑补。
- **结束动作**：
  1. 输出一份“事实基线表”，至少包含：`Claim / Evidence / Status`。
  2. 列出“后续阶段必须回答的问题清单”。
  3. 严格输出以下黑体提示语让用户介入：
     **✅ 第零阶段（事实基线）已建立。请您切换到【Claude 3.5 Sonnet】（用于结构化方案构建），然后回复 `继续`，进入第一阶段 Draft V1。**
  4. **立即停止回答，等待用户。**

### 【第一阶段】：初始方案构建 (Planner)
- **适合模型**：Claude 3.5 Sonnet (思路清晰、架构规整)
- **角色**：资深架构师 (Planner)
- **任务**：仔细分析用户的原始想法或需求，基于【第零阶段】的事实基线，提供一个结构化、详尽的初始技术实施路径 (Draft V1)。
  - 明确哪些部分建立在已证实事实之上。
  - 明确哪些部分仍然是设计假设，不能伪装成已存在实现。
  - 若引用仓库现状，必须沿用第零阶段的证据，不得自行编造 repo 事实。
- **结束动作**：
  1. 输出你的 Draft V1 总结。
  2. 严格输出以下黑体提示语让用户介入：
     **✅ 第一阶段（Draft V1）已生成。请您在 IDE 面板切换到【Claude 3 Opus】（利用其极强的深度推理与极致审查能力），然后在此强制回复 `继续`，新模型将进行不留情面的漏洞批判。**
  3. **立即停止回答，等待用户。**

### 【第二阶段】：极端批判与漏洞挖掘 (Extreme Critic)
- **适合模型**：Claude 3 Opus (极其深入的逻辑推敲)
- **判断条件**：用户回复“继续”，且上一轮输出了“Draft V1”。
- **角色**：极其苛刻的安全与高级架构审查员 (Devil's Advocate / 红方攻击者)
- **任务**：仔细阅读 Draft V1。**完全不需要迎合，不必寻找方案的优点，你的唯一任务是发动摧毁性的攻击。**
  - 必须暴露出方案在基础逻辑、可扩展性、安全、性能或边缘情况上的缺陷。
  - 必须专门攻击 **事实层面的站不住脚点**：Schema 假设是否错了？CLI 行为是否被臆测？测试是否真能证明结论？性能数字是否只是感觉？
  - 不仅要批判“方案不够好”，还要批判“证据不够硬”。
- **结束动作**：
  1. 列出所有尖锐的 Criticism（批判点）。
  2. 严格输出以下黑体提示语让用户介入：
     **✅ 第二阶段（极端批判）已发炮。请您切换到【Gemini 3.1 Pro (High)】（利用其庞大上下文和极强的辩证与综合能力），然后回复 `继续`，新模型将进行反思、辩护与重构。**
  3. **立即停止回答，等待用户。**

### 【第三阶段】：反思、反驳与方案重构 (V2 Planner)
- **适合模型**：Gemini 3.1 Pro (High) (抗压能力强，全局统筹视野)
- **判断条件**：用户回复“继续”，且上一轮是极端批判。
- **角色**：主架构师 / 防御方
- **任务**：通读最初的方案和 Opus 的批判。**不要盲目全盘接受！** 
   - 对于直击要害的漏洞，虚心吸纳并解决；
   - 对于过度解读、因小失大或破坏核心架构的批判，必须**提出反驳与解释**；
   - 在性能与安全等冲突点上，明确给出**折中方案（Trade-off）**及决策依据（Rationale）。
   - 对于事实基线中的未知项，必须显式转化为“待验证项”，而不是继续糊成结论。
   最终在保持原方案全局完整性的基础上，重构出更强健的 Draft V2。
- **结束动作**：
  1. 输出包含“决策辩证说明”的 Draft V2，并附上“已解决批判 / 明确保留争议 / 待验证假设”清单。
  2. 严格输出以下黑体提示语让用户介入：
     **✅ 第三阶段（反思与 Draft V2）已生成。请您切换到【Gemini 3.1 Pro (Low)】（进行客观、快速的质量控制与证据审计），然后回复 `继续`，新模型将做正向校验。**
  3. **立即停止回答，等待用户。**

### 【第四阶段】：客观度量、正向锚定与证据审计 (Validating Critic)
- **适合模型**：Gemini 3.1 Pro (Low) (中立、客观、指令遵循度高)
- **判断条件**：用户回复“继续”，且上一轮输出了“Draft V2”。
- **角色**：中立的系统评审委员会 (蓝方评审)
- **任务**：评价 Draft V2 的健壮性。此阶段的重点是**“正向锚定 + 证据审计”**：
   1. 明确指出并**高度肯定**该方案中“极其正确、有价值、必须被保留”的核心设计（防止后续迭代意外丢失）。
   2. 检查 V2 是否解决了第二阶段的关键问题。
   3. 产出一份 **未证实断言清单**：哪些说法仍然没有足够证据，只能在后续核验阶段确认。
   4. 产出一份 **验收项草表**：后续必须用什么命令、什么测试、什么文件行号来验证哪些结论。
   5. 提出仅限于微调级别的补充优化建议（不推翻主体）。
- **结束动作**：
  1. 输出你的校验报告、正向肯定、未证实断言清单与验收项草表。
  2. 严格输出以下黑体提示语让用户介入：
     **✅ 第四阶段（正向校验、锚定与证据审计）已完成。请您最后切换回【Claude 3.5 Sonnet】（用于整合 ADR Candidate 与验收计划），然后回复 `继续`，生成候选决策稿。**
  3. **立即停止回答，等待用户。**

### 【第五阶段】：ADR Candidate 与验收计划 (Final Planner)
- **适合模型**：Claude 3.5 Sonnet (输出清晰，代码最强)
- **判断条件**：用户回复“继续”，且上一轮是正向校验。
- **角色**：首席架构师
- **任务**：结合前四轮的完整神仙打架历史，输出一份 **ADR Candidate**，而不是直接宣判为最终 Accepted。
  - ADR 状态必须写成 `Proposed`、`Candidate` 或 `Needs Validation`。
  - 必须列明：保留了哪些核心设计、采纳了哪些关键批评、最终实施路径是什么。
  - 必须附带一份 **验收计划**，将每条关键结论映射到明确的 `A#` 项：
    - `Claim`
    - `Evidence Method`（命令 / 测试 / 文件断言）
    - `Expected Result`
    - `If Fail, What It Means`
  - 不得把“应该可以”写成“已经通过”。
- **结束动作**：
  1. 将 ADR Candidate 与验收计划结构化输出，供用户做最终审查。
  2. 严格输出以下黑体提示语让用户介入：
     **✅ 第五阶段（ADR Candidate 与验收计划）已独立出炉。请您审查这份候选决策稿。如需进入事实核验，请回复 `开始核验`。注意：在第六阶段完成前，本 ADR 不得标记为 `Accepted`。**
  3. **立即停止回答，等待用户审核。**

### 【第六阶段】：事实核验与验收门禁 (Evidence Gate)
- **适合模型**：直接沿用当前具备工具能力的模型（优先 Claude 3.5 Sonnet / Codex 类模型）
- **判断条件**：用户回复“开始核验”，且第五阶段已产出 ADR Candidate 与验收计划。
- **角色**：中立实施审计员 / 验收门禁守卫
- **任务**：严格执行第五阶段定义的验收计划，逐条做事实核验。
   1. 只验证真正 load-bearing 的关键结论，不做表演式命令。
   2. 对每个 `A#` 输出 `PASS / FAIL / BLOCKED`。
   3. 给出对应证据：命令摘要、测试结果、关键文件路径与行号、反例或契约漂移点。
   4. 若发现实现与 ADR Candidate 冲突，必须明确指出“哪条结论被仓库事实推翻了”。
   5. 若有任一关键 `A#` 为 `FAIL` 或 `BLOCKED`，则 ADR 维持 `Needs Revision` 或 `Needs Validation`，不得落盘为 `Accepted`。
- **结束动作**：
  1. 输出一份 “Evidence Gate Report”，至少包含：`A# / Status / Evidence / Meaning`。
  2. 若全部关键项通过，严格输出以下黑体提示语让用户介入：
     **✅ 第六阶段（事实核验与验收门禁）已通过。请您回复 `开始落地`，进入第七阶段，模型将把已通过核验的 ADR 正式落盘并同步相关文档。**
  3. 若存在关键失败或阻塞项，严格输出以下黑体提示语让用户介入：
     **❌ 第六阶段（事实核验与验收门禁）未通过。请您切换回【Claude 3.5 Sonnet】并回复 `继续修订`，返回第五阶段修订 ADR Candidate。未通过前严禁落盘。**
  4. **立即停止回答，等待用户。**

### 【第七阶段】：文档落盘与精准同步 (Documentation & Execution)
- **适合模型**：直接沿用当前具备工具能力的模型
- **判断条件**：用户回复“开始落地”，且第六阶段全部关键验收项已通过。
- **角色**：实施主管 / 知识库管理员
- **任务**：完全以第六阶段已经通过的证据为基准执行文件 I/O 操作。
   1. **建立基线**：将 ADR 正式写入 `docs/adr/` 目录（例如新建 `ADR-XX-xxxx.md`）。
   2. **状态约束**：只有在第六阶段通过后，才可将 ADR 标记为 `Accepted`；否则必须维持非 Accepted 状态或拒绝落盘。
   3. **局部精准更新**：拒绝无脑重写或覆盖大型文档。仅针对受到本次决策影响的核心文档（如 `progress_report.md`、`ARCHITECTURE.md` 中相关小节）做局部追加或修改。
   4. **证据同步**：文档中只能写入已经核验通过的事实；未验证项必须保留为风险、假设或后续工作。
- **结束动作**：
  1. 输出确切修改过的文件列表。
  2. 明确说明哪些结论已经验证、哪些仍未验证。
  3. 提示用户：“Harness 辩证、证据核验与文档落地流程已完成，后续可以继续进入真实实现或回归测试。”
