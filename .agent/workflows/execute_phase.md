---
description: 自动执行和落地阶段任务工作流 (Phase Execution Workflow)
---

这是一个规范化代码落地的工作流，用于承接 Harness 辩证后形成的技术方案（如 `test_plan_XX.md`）。
其核心目的是：**绝对捍卫 Harness 阶段的心血与 Token 投资**。如果代码落地阶段产生回归 Bug 未被发现，Harness 阶段的高维思考将被瞬间击穿。因此，本工作流强制引入**跨模型的物理拦截与 Codex 审查点**。

作为执行落地的大模型，你需要严格遵循以下阶段化步骤：

### 核心训诫 (Core Directives)：
- **防御性开发**：必须将旧系统视作易碎品。
- **强制跨模型审查**：不要试图“自己查自己的错（因为模型存在上下文思维惯性）”，必须逼迫用户使用外部模型（IDE Codex 扩展或其他模型）进行物理隔离的查错。
- **踩刹车机制**：每个阶段结束时，**必须立刻停止回答**，等待用户指令，绝对不可以一次性把所有流程跑完！
- **契约先行 (Contract-First Gate)**：修改任何核心业务代码之前，必须先修改或编写针对该改动的破坏性用例（红测），然后再进行业务编码。
- **强制微提交 (Micro-Commits)**：高风险重构时，一旦某个关联子模块验证通过，必须先 `git add` 并 `git commit`，将风险截断，方便一键回滚。
- **零信任基线原则（ADR-63）**：编码开工前，必须确认 pytest 基线为全绿。带病开工等于盲目施工——红灯变红灯时无法分辨新旧债务。

---

### 【第一阶段】：深度理解与爆炸半径分析 + 架构划区 (Blast Radius Analysis & Zone Declaration)
**[执行动作]**
1. 读取指定的 `Phase XX` 阶段任务或计划文档。
2. 仔细检查当前项目中将被影响的核心代码文件。
3. 生成 `implementation_plan.md` 伪影制品。
4. **强制要求**：在该计划中单开一章 **【爆炸半径评估 (Blast Radius Analysis)】**，明确列出：本次改动极有可能会波及哪些历史功能？
5. **强制要求（ADR-63）**：紧跟爆炸半径评估，追加 **【架构划区与回归域 (Zone Declaration)】** 章节。将本次改动归属至以下三区之一（只需声明区域 + 对应命令，**禁止猜测单个测试文件名**）：
   - **ZONE A（核心引擎层）** 波及 `loop.py`, `context.py`, `session/manager.py`, `middleware/`, `verification.py` 等核心链路
     👉 靶向命令：`pytest tests/test_loop*.py tests/test_session*.py tests/test_middleware*.py tests/test_phase31*.py tests/adversarial/ -W ignore -v`
   - **ZONE B（工具与技能层）** 波及 `tools/`, `channels/`, `skills/`, `cron/` 等外围组件
     👉 靶向命令：`pytest tests/test_<具体工具名称>.py tests/test_channel*.py -W ignore -v`
   - **ZONE C（配置与基础设施层）** 波及 `config/`, `docs/`, `scripts/` 等非执行路径
     👉 靶向命令：按受影响的具体模块精准执行，或无需测试

**[结束动作]**
输出以下黑体提示语，并**立即停止回复**：
**✅ 第一阶段：落地方案与架构划区完毕（详见 implementation_plan.md）。请审查。**
**⚠️【绿色基线快照 (Green Baseline)——ADR-63 铁律】在回复 `开始编码` 之前，请务必先在终端运行上方 Zone 对应的 `pytest` 靶向命令，确认测试基线为全绿。若基线已红，禁止开工——先修 Bug！如无法运行测试，请明确告知。**

### 【第二阶段】：安全驱动的代码实施 (Rigorous Execution)
**[执行动作]** 
*（触发条件：用户回复“开始编码”）*
1. 创建 `task.md` 制品。
2. 开始独立执行代码修改。如果是 **ZONE A** 的高风险改动，必须**先手编写 Adversarial Tests（对抗性恶意边界用例）**。
3. 尝试运行项目中现有的测试程序（如 `pytest`），或顺手为新的核心链路增加基础测试断言。完成代码闭环。
**[结束动作]**
代码写完后，输出以下黑体提示语，并**立即严格停止回复，进入等待状态**：
**⏸️ 第二阶段完毕（代码已落地）。**
**🚨【零信任物理拦截——ADR-63 双层串联门控】🚨 两步必须串联，L1 全绿才能触发 L2，缺一不可：**
**Step 1 — 机器检查（L1：确定性防线）**：请在终端再次运行第一阶段确认的 `pytest` 靶向命令（与基线快照对比）。若出现新增红灯，请将错误日志发给我立即修复，无需进入 Step 2。
**Step 2 — 自动化 L2 语义审查（L2：仅在 Step 1 全绿后触发）**：
作为 Agent，摒弃通过人类用户去粘帖的流程。你必须在终端亲自运行自动化审查脚本：
`python .agent/scripts/auto_reviewer.py --context "此处用 50 字内概述本次核心审查目标"`
（建议按需追加 `--files <具体波及文件>` 缩小审查防止 Token 爆炸）。

一旦脚本在终端打印出 **[CODEX L2 REVIEW RESULTS]**：
1. 请仔细通读它的审查意见。
2. **🚨 跨模型防暴走拦截机制 (Human Intervention Gate)**：
   如果审查意见中包含任何 A 级 / B 级残留，你**绝对不可以偷偷擅自尝试自动修复！**
   你必须立即停止当前动作，将 Codex 输出的《分类残留表》原样摘出向用户报告，附上你的“针对性修复计划”，并明确询问：“**发现 L2 审查拦截，是否允许我执行上述修复计划？**”
   只有用户回复“允许”后，你才能进入第三阶段（修复重铸）。
3. 如果连续两轮修复均被打回，强制要求用户创建新 Session 以防上下文错乱。
**若脚本返回审查结果为全数通过：请向用户明确回复 `自动化 L2 审查通过，开始收尾`。**

### 【第三阶段】：回炉重造 (Bug Fixing Loop) - *【可选阶段】*
**[执行动作]**
*（触发条件：用户粘贴了 Codex 或其他模型指出的按大类收敛的审查意见）*
收到外部审查意见后，作为 Agent 必须**极其苛刻地遵循以下纪律进行修复**：
1. **证据定级与免举证拦截**：若 Codex 给出的风险属于 C 级纯理论担忧，果断将其列入已知清单并拒绝无效修复；若属 A/B 级风险，立刻展开修复。
2. **拒绝“头痛医头”**：绝不能顺着 Codex 给出的具体函数名一补了之。必须追问：“这是不是同类架构问题的另一个入口变种？”并将其合并入顶层的大类树。
3. **触底反弹的 Stop Rule (两轮止损法则)**：如果在同一大类问题上，你已经被 Codex 打回了两次（连续两轮同类回归），**立刻停止针对该函数的修补！**这说明底层根因（Root Cause）根本没防住。必须全盘推翻之前的思路，强制寻找物理级/系统级的升维重构方案（例如黑转白名单、彻底换元执行），禁止继续打低级补丁。
4. 修改完毕后，**重新构建第二阶段的结束动作**。向用户报告你一次性锁死了哪个大类别，并按照重塑后的状态继续输出 Step 2 的专用 Prompt，要求 Codex 进入下轮基于分类的严苛复查。

### 【第四阶段】：文档三权分立与靶向测试 (Wrap-up & Targeted Manual Tests)
**[执行动作]**
*（触发条件：用户回复“审查通过，开始收尾”）*
审查最终通过后，遵循以下更新法：
1. **[经验法则归档]**：在刚才开发与 Codex 纠错中踩到的教训，追加到 `docs/rules/ARCHITECTURE.md` 尾部。
2. **[技术细节冷藏]**：将方案详情追加归档至 `docs/archive/`。
3. **[进度极简追踪]**：在 `progress_report.md` 用一句话勾掉任务。
4. **[靶向人工测试手册]**：生成 `docs/tests/manual_guides/phase_XX_manual_test_guide.md`。除新功能验收外，必须单开一篇 **【连带回归靶点 (Regression Targets)】** 模块，从爆炸半径分析中提取最容易受损的历史功能，指导用户进行精确定向测试。
**[结束动作]**
向用户发送如下黑体提示：
**🎉 代码实施、物理 Codex 跨模型审查、系统文档与靶向测试指南均已彻底竣工！本次落地已锁死安全性。请参考手册进行终审，过后可使用 `/execute_phase` 开启下阶段会话。**
